# SW 시스템 테스트 케이스 생성

테스트 베이시스(요구사항 사양서 등)를 분석해 **실행 가능한** 시스템 테스트 케이스를 설계하고, 검증 스크립트를 통과한 엑셀 파일로 납품한다.

이 결과물은 A-SPICE 심사와 ISO 26262 안전 심사에서 증거물로 쓰인다. 심사자는 (1) 모든 요구사항이 테스트로 덮였는지, (2) 모든 테스트가 요구사항으로 거슬러 올라가는지, (3) 테스트 케이스가 어떤 기법으로 왜 도출됐는지, (4) 합격/불합격을 판정할 수 있는지를 본다. 아래 규칙은 모두 이 네 가지를 위한 것이다. 상세 근거는 `references/standards.md`, 기법 적용법은 `references/techniques.md`를 필요할 때 읽는다.

## 작업 흐름

### 1. 입력 확인

- **테스트 베이시스**: 사용자가 준 요구사항 문서(xlsx, docx, pdf, md, 붙여넣은 텍스트 등)를 끝까지 읽는다. 각 요구사항의 ID, 내용, (있다면) ASIL·출처를 뽑는다.
  - ID가 없으면 `TB-001`처럼 부여하고, 부여했다는 사실을 최종 보고에 적는다.
  - 하나의 ID에 여러 조건이 섞여 있으면 ID는 그대로 두고 조건별로 테스트를 나눈다(ID를 임의로 쪼개지 않는다 — 추적 대상은 원래 ID다).
- **양식**: 사용자가 테스트 케이스 양식(엑셀)을 주면 그 양식을 따른다(5단계의 `--template`). 없으면 기본 항목을 쓴다:
  테스트 케이스 ID, 테스트 베이시스 ID, 테스트 목적, 사전 조건, 입력값, 절차, 예상 출력값, 사용한 테스트 기법, 구분(제안 여부), 테스트 환경, 비고.
- 베이시스나 출력 위치가 정말 없으면 그때만 사용자에게 묻는다.

### 2. 테스트 베이시스 분석

요구사항마다 다음을 정리한다(작업 메모로, 결과물에 다 넣을 필요는 없다).

- 기능/비기능 분류. 비기능 = 타이밍·응답 시간, 주기, 자원(CPU·메모리), 성능, 강건성(robustness)·고장 주입, 진단, 시동/종료, 통신 부하 등. 한 요구사항에 둘 다 있으면 각각의 시트에 케이스를 만든다.
- 입력 파라미터와 그 범위·해상도·단위, 상태(모드), 출력과 관측 방법, 시간 조건.
- **테스트 가능성**: 예상 결과를 요구사항에서 도출할 수 없거나 값이 모호하면(“빠르게”, “적절히”) 추측해서 쓰지 않는다. 가장 합리적인 해석으로 케이스를 만들고, 그 가정을 `비고`에 적고, `issues`(확인 필요 시트)에 올린다. 이렇게 하면 커버리지 100%를 유지하면서도 근거 없는 기대값을 숨기지 않는다.

### 3. 테스트 케이스 설계

각 요구사항에 대해 아래 기법을 순서대로 검토한다. 기법 이름은 시트에 정확히 이 표기로 쓴다(검증 스크립트가 이 이름을 센다).

| 기법 표기 | 적용 |
|---|---|
| `동치 클래스` | **필수.** 입력·상태마다 유효/무효 클래스를 정의하고 각 클래스를 최소 1회 시험한다. |
| `경계값 분석` | **필수.** 순서가 있는 범위(수치, 시간, 개수)마다 경계와 그 바로 바깥값을 시험한다. 간격(δ)은 사양의 해상도를 따른다. |
| `페어와이즈` | 독립 파라미터가 3개 이상이고 조합 상호작용이 의미 있을 때 적용한다. **반드시 PICT로 도출한다**(4단계). |
| `WoW 검증` | 엣지 케이스. 경계·조합의 극단, 시간 경계, 동시 발생, 전원/통신 중단 등(아래 참고). |
| `요구사항 분석`, `오류 추정`, `고장 주입`, `운용 시나리오` 등 | ISO 26262-6이 권장하는 그 밖의 기법. 비기능·안전 요구사항에 특히 유용하면 쓴다. |

한 케이스가 여러 기법에 해당하면 모두 적는다(예: `동치 클래스, 경계값 분석`). 범위가 없는 요구사항(단순 on/off 등)은 경계값이 성립하지 않는다 — 억지로 만들지 말고 동치 클래스만 적용한다. 다만 결과물 전체에서 두 필수 기법이 모두 쓰여야 하며, 경계를 가진 입력이 하나라도 있으면 반드시 경계값 분석이 있어야 한다.

**WoW 검증 (엣지 케이스)**: 일반 기법으로는 잘 안 나오지만 실제 결함이 숨기 쉬운 지점이다. 예: 여러 입력이 동시에 경계에 있음, 상태 전이 직후/직전 같은 시간 경계, 입력이 디바운스 시간 근처에서 토글, 시동 직후 첫 주기, 카운터·타이머 오버플로, 통신 메시지 누락 직후 복귀, 동작 중 전원 리셋, 동일 요청의 연속 반복. 사양이 그 상황의 동작을 정하고 있으면 일반 케이스로, 정하지 않았으면 `제안` 케이스로 만든다.

**쓰레기 케이스 금지**: 커버리지 숫자를 채우려고 케이스를 늘리지 않는다. 모든 케이스는 다른 케이스가 덮지 않는 무엇(새 동치 클래스, 새 경계, 새 조합, 새 위험)을 시험해야 하며, 그 이유가 `테스트 목적`에 드러나야 한다.
- 유효 클래스끼리는 한 케이스에 묶어도 된다. 무효 클래스는 서로를 가리지 않도록 한 케이스에 하나씩만 넣는다.
- 입력과 예상 결과가 같은 케이스는 하나로 합친다(스크립트가 중복을 오류로 잡는다).

**실행 가능성**: 시험자가 질문 없이 바로 수행하고 합격/불합격을 판정할 수 있어야 한다.
- 입력은 구체적인 값과 단위로 쓴다(“고속” 대신 `차속 = 120 km/h`). 신호/파라미터 이름은 베이시스의 이름을 쓴다.
- 절차는 시스템 수준에서 실제로 조작 가능한 단계로 쓴다(번호 매긴 단계). 내부 변수 직접 조작이 필요하면 그 수단(진단 서비스, 캘리브레이션 도구, 고장 주입 장치)을 명시한다.
- 예상 출력값은 관측 가능한 값과 허용오차·시간 조건으로 쓴다(`200 ms 이내에 경고등 ON`). “정상 동작한다”, “적절히 처리한다”만으로는 판정할 수 없다.
- 사전 조건(전원 상태, 모드, 초기값)을 적는다.

**제안 케이스**: 베이시스가 요구하지는 않지만 시험할 가치가 있다고 판단한 케이스(사양이 정하지 않은 엣지 동작, 추가 강건성 시험 등)는 `구분`에 `제안`으로 표시한다. 제안 케이스도 관련된 베이시스 ID에 추적시키되, 커버리지 계산에는 넣지 않는다 — 커버리지가 제안 케이스에 기대면 베이시스가 실제로 덮였다고 말할 수 없기 때문이다.

**ID 규칙(양식이 따로 정하지 않은 경우)**: 기능 `STC-F-001`, 비기능 `STC-NF-001`.

### 4. 페어와이즈 (PICT)

조합 대상 요구사항이 있으면 PICT로 조합을 만든다. 손으로 조합을 고르지 않는다 — 도출 과정이 재현 가능해야 심사에서 근거가 된다.

1. PICT 준비: `python <skill>/scripts/get_pict.py` → 출력된 경로가 pict 실행 파일이다(이미 있으면 다시 받지 않는다).
2. 모델 파일 작성: 파라미터는 동치 클래스의 대표값(필요하면 경계값)으로 정한다. 물리적으로 불가능하거나 사양상 금지된 조합은 제약(`IF ... THEN ...;`)으로 제거한다 — 실행 불가능한 케이스를 만들지 않기 위해서다. 문법은 `references/techniques.md`.
3. 실행: `python <skill>/scripts/run_pict.py <모델파일> --out <rows.json> [--pict <경로>] [-- <pict 옵션>]` (기본 2-way).
4. PICT가 만든 행 하나가 테스트 케이스 하나다. 각 행에 예상 출력값을 베이시스로부터 채운다. 모델과 생성 행은 `pairwise` 항목에 남겨 엑셀의 `페어와이즈` 시트에 기록되게 한다.

PICT를 받을 수 없는 환경이면(오프라인 등) 페어와이즈 케이스를 직접 만들지 말고, 그 사실을 사용자에게 알리고 모델 파일만 남긴다.

### 5. 엑셀 생성과 검증

설계 결과를 JSON 파일 하나로 쓴다(스키마는 아래). 그다음:

```
python <skill>/scripts/build_workbook.py <cases.json> --out <결과.xlsx> [--template <양식.xlsx>]
```

스크립트는 다음을 검사하고 오류가 있으면 엑셀을 만들지 않는다(종료 코드 1):
- 모든 베이시스 ID가 제안이 아닌 케이스로 1개 이상 덮였는가 (커버리지 100%)
- 모든 케이스가 존재하는 베이시스 ID를 가리키는가 (추적성 100%, 고아 케이스 없음)
- 필수 항목 누락, 케이스 ID 중복, 입력+예상 결과가 같은 중복 케이스
- 두 필수 기법 사용 여부

경고(모호한 표현, 기법 미사용 등)는 엑셀은 만들되 출력한다. **오류는 0개, 경고는 하나씩 검토해서 고칠 것은 고친 뒤** 납품한다. 검사를 통과시키려고 케이스 내용을 비우거나 의미 없는 케이스를 추가하지 않는다.

생성되는 시트: `기능 테스트`, `비기능 테스트`, `추적성 매트릭스`, `커버리지 요약`, (있으면) `페어와이즈`, `확인 필요`.

양식을 쓰면 시트를 앞에서부터 훑어 머리글 행이 있는 첫 시트(표지·개정 이력 시트는 건너뜀)를 찾아 열 이름으로 항목을 맞추고(예: `요구사항 ID` → 베이시스 ID, `기대 결과` → 예상 출력값), 그 시트를 기능/비기능 두 시트로 복제해 채운다. 양식에 베이시스 ID·기법·구분 열이 없으면 추적성과 제안 표시를 위해 끝에 추가한다. 판정·실행 결과·시험자처럼 실행 시 채우는 열은 비워 둔다. 경고로 나오는 매핑 결과를 확인해 잘못 짝지어진 열이 없는지 본다.

**Python 실행**: Windows에서 `python`이 Microsoft Store 바로가기로 연결돼 실행되지 않으면 `py` 또는 설치된 python.exe의 전체 경로를 쓴다. openpyxl이 없으면 `python -m pip install openpyxl`.

### 6. 보고

사용자에게 짧게 알린다: 파일 경로, 베이시스 수와 커버리지, 기능/비기능/제안 케이스 수, 기법별 케이스 수, PICT 사용 여부, `확인 필요` 항목(사양 모호점) 요약, ID를 새로 부여했는지.

## JSON 스키마

```json
{
  "project": "프로젝트명",
  "document_id": "STS-XXX (선택)",
  "version": "1.0",
  "test_basis": [
    {"id": "SRS-001", "title": "요약", "text": "요구사항 원문", "type": "기능", "asil": "B"}
  ],
  "test_cases": [
    {
      "id": "STC-F-001",
      "basis_ids": ["SRS-001"],
      "category": "기능",
      "objective": "차속 유효 범위 하한 경계에서 경고 미출력 확인",
      "preconditions": "IGN ON, 경고등 OFF",
      "inputs": "VehicleSpeed = 0 km/h",
      "procedure": ["VehicleSpeed를 0 km/h로 설정한다", "500 ms 대기한다", "WarningLamp 상태를 확인한다"],
      "expected": "WarningLamp = OFF 유지",
      "techniques": ["경계값 분석", "동치 클래스"],
      "proposal": false,
      "environment": "HIL",
      "notes": ""
    }
  ],
  "pairwise": [
    {"name": "모드 조합", "basis_ids": ["SRS-010"], "model": "PICT 모델 원문", "options": "/o:2", "rows": [{"Mode": "ECO"}], "case_ids": ["STC-F-020"]}
  ],
  "issues": [
    {"basis_id": "SRS-005", "issue": "응답 시간 미정의", "assumption": "100 ms로 가정", "case_ids": ["STC-NF-003"]}
  ]
}
```

- `type`/`category`는 `기능` 또는 `비기능`. `test_basis[].type`은 생략 가능.
- `procedure`는 문자열 배열(번호는 스크립트가 붙인다).
- 사용자 양식이 다른 열(예: 우선순위, 시험자)을 가지면 테스트 케이스 객체에 그 열 이름 그대로 키를 추가하면 스크립트가 같은 이름의 열에 채운다.
