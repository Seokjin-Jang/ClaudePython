## 1. 방법

- 모든 모듈을 TDD로 구현했다 (`test-driven-development` 스킬). 모듈마다 시험을 먼저 쓰고, 실패(RED)를 확인한 뒤 구현(GREEN)했다.
- 시험 설계 기법: 동치 분할(유효/무효 입력), 경계값 분석(0.0/300.0 km/h, 3.0 km/h, 0.200 s, 10.0 s, 100건), 규칙 쌍 조합(SWR-019 인접 순위 9쌍), 결함 주입(기록 콜백 예외, 직렬화 실패).
- 시험마다 docstring에 잡으려는 결함과 `@req` 요구 ID를 적었다.

## 4. 시험 중 발견·조치

| ID | 내용 | 조치 |
|---|---|---|
| UT-F-01 | 부동소수 뺄셈 오차로 1.3 − 1.1 = 0.2000000000000002가 되어 0.200 s 경계를 지연으로 잘못 판정할 수 있음 | 시간 비교를 마이크로초 정수로 변경 (SWD-001 D-01), 경계 시험 추가 |
| UT-F-02 | Python에서 `bool`이 `int` 하위형이라 차속 `True`, 불리언 `1`이 통과할 수 있음 | `type(x) is bool`, bool 제외 숫자 검사 (D-03, D-04) |
| UT-F-03 | 결과가 요청과 같은 경우(주행 중 lock 요청)를 거절로 기록하는 오탐 가능 | 출력이 요청과 다를 때만 `DRIVER_REQUEST_REJECTED` 기록, 시험 추가 |

## 5. 한계

- TDD 사이클을 모듈 단위로 진행했다. 한 모듈의 시험 여러 개를 먼저 쓰고 함께 실패를 확인한 뒤 구현했으며, 시험 하나씩 RED→GREEN을 반복하지는 않았다.
- 스텁 상태에서 이미 통과한 시험이 있다: "지연 아님", "억제 없음", "결정론(None == None)", "해시 불일치 시 1" 같이 스텁의 기본 반환값과 기대값이 같은 경우다. 이 시험들은 구현 후에도 통과하며, 반대 방향 시험(지연임, 억제함 등)이 같은 동작을 실패로 확인했다.
